git squash-1:
لو الـ feature branch  فيه كذا small commit، الـ squash بيقدر يدمجهم كلهم في commit واحد، وده بيخلي الـ history بتاع المشروع أبسط وأنضف.

لكن عيبه إن الـ squash رغم أنه بيحافظ على ال commits الي اتعملت ،  بيمسح تفاصيل كل individual commit، وبالتالي بنفقد القدرة على تتبع التسلسل بتاع ال small commits



ملحوظة:  git squash مش command هو concept  نقدر ننفذها بطرق مختلفة، ومن أشهرها git rebase -i


سيناريو: أثناء تطوير Shopping Cart في مشروع، عملت كذا commit صغير، زي إضافة الـ cart، و fix لل calculation بتاع ال price، وfix لمشكلة في الـ quantity.
 قبل ما أعمل merge للـ feature branch، بستخدم squash لدمج الـ commits دي في commit واحد، بحيث يكون الـ commit history أبسط وأسهل في المراجعة

مثال: ال commits كانت بالشكل ده

 Add shopping cart
Fix price calculation
Fix quantity

فبقت:

Implement shopping cart

وده مناسب لما تكون الـ commits الصغيرة دي كلها جزء من feature واحدة ومش محتاجين نحتفظ بتفاصيل ال history بتاع تطوير ال feature

2-git merge  vs  git rebase  :

git merge: بعد ما نخلص الشغل على feature branch، نقدر تستخدم git merge علشان ننقل التغييرات بتاعتنا للـ main branch. الـ Merge بيجمع الـ content الموجود في ال 2branches ،
 مع الحفاظ على ال commit history بتاع كل branch، وبيعمل merge commit يوضح إن عملية الـ integration تمت.

ميزة الـ merge إنه بيحافظ على الـ full record لكل الـ commits، فبالتالي نقدر بسهولة نعرف كل developer عمل إيه، وده بيكون مفيد جدًا خصوصًا في الـ team projects.
 لكن لو بنعمل merge بشكل متكرر، ممكن الـ commit history يبقى معقد، خصوصًا لما يكون فيه كذا branch بيتعمله merge في نفس الوقت.


سيناريو: أنا شغال مع team على مشروع، وزميلي كان شغال على payment feature في branch اسمه payment. بعد ما خلص الـ feature واختبره، 
عايز يضيف شغله للـ main branch من غير ما يتم حذف أو تغيير الـ commit history بتاعه. لذلك أستخدمنا git merge علشان ندمج الـ payment branch مع الـ main، 
وبكده تفضل كل الـ commits الخاصة بشغله موجودة ونقدر نعرف هو عمل إيه أثناء تطوير الـ feature.

مثال: 
git checkout main
git merge payment




git rebase: بتعمل integration للتغييرات من branch ل branch تاني، لكن بطريقة مختلفة.   rebase بتاخد كل commit موجود في الـ current branch وبتعمله reapply فوق الـ target branch 
وليكن ال main، كأن الـ commits دي كانت معمولة من البداية فوق آخر نسخة من الـ target branch.

بما إن الـ rebase بتعمل recreate للـ commits، فهي بتغير الـ commit history. أهم ميزة للـ rebase إنها بتخلي الـ commit history أنضف وأبسط من غير تغقيد، وده بيخلي تتبع التغييرات الي تمت أسهل بكتير

لكن بما إن كل commit بيتعمله reapply، ممكن تضطر نحل الـ conflicts أكتر من مرة، وده ممكن يخلي الموضوع أعقد شوية. والنقطة المهمة اللي لازم تفتكرها إن الـ rebase بيغير الـ history، 
وعشان كده مش بيُفضل استخدامها على branches اتعمل لها share بالفعل مع باقي الـ developers، لأن تغيير الـ history ل branch مشترك ممكن يعمل conflicts ومشاكل لباقي الناس اللي شغالة على نفس الـ branch.



سيناريو: 
أنا شغال على E-commerce project وعندي product branch بضيف فيه ميزة Product Search. أثناء ما أنا شغال، زميلي عمل تعديلات جديدة ورفعها على main branch. قبل ما أعمل merge للـ product branch، 
بستخدم git rebase main علشان أخلي التعديلات بتاعتي مبنية على أحدث نسخة من main، وبالتالي يكون الـ commit history أنضف  وأسهل في المتابعة.

مثال: 

git checkout product
git rebase main

4- git cherry pick : 
بستخدمها لو عندي 2 branches  هما: main  و feature branch وفيه commit  معين في ال feature branch  محتاج أطبقه على ال main  بدون ما أعمل merge لل branch  كله

سيناريو: أثناء شغلي على مشروع، كان فيه payment branch عليه عدة commits، لكن كنت محتاج إصلاح معين موجود في commit واحد فقط من غير ما أضم باقي التغييرات الموجودة في الـ branch. 
في الحالة دي بستخدم git cherry-pick علشان أنقل التغييرات الموجودة في الـ commit المطلوب فقط إلى الـ main branch، من غير ما أعمل merge للـ branch بالكامل

كالتالي: ال branch  فيه أكتر من commit  هم: 
Add payment
Add validation
Fix payment bug
Update UI
Fix button

اكتشفت إن Fix payment bug فقط فيه fix مهم جدًا ومحتاجه في main.

فهنقف على ال main  بواسطة : git checkout main 

وبعدها: git cherry-pick abc123

حيث: abc123 هي ال commit hash  بتاعت  fix payment bug

5- git clean : 
بستخدمها لتنظيف المشروع من الملفات والـ folders الـ Untracked.

لكن يفضل قبل ما أحذف حاجة أكتب: git clean -n

عشان أعرف ايه الحاجات الي هتتحذف قبل ما أحذفها 
وبعد ما أتأكد هكتب: 
git clean -f
عشان يتم الحذف 

وفي حالة أننا عايزين نحذف folders   كمان هنكتب: 

git clean -fd


سيناريو: لو عندي ملفات المشروع كالتالي: 
project/
├── Program.cs
├── README.md
├── test.txt
├── output.txt
└── temp/

وعندي test.txt  و output.txt  و /temp  دول untracked 
هستخدم: 
git clean -fd

8- git bisect: 

بستخدمها في حالة أني عملت أكتر من commit  وظهر bug  وأنا مش متأكد هو ظهر بعد أي commit  فيهم لكن أنا عارف المشروع كان شغال كويس لحد commit  معين 

سيناريو: عندي تسلسل commits  كالتالي : A → B → C → D → E → F → G 

هكتب: git bisect start 

وبعدها هقوله أن ال commit  الي أنا واقف عليه فيه bug  : git bisect bad 

وهحددله أخر commit  كان مفيهوش bug ( في حالتنا C (:   git bisect good C 


Git هيختار Commit من المنطقة الموجودة بين C وG بحيث يقسم  الـ commits لنصين 

فلو اختار E  هختبره لو مش تمام هقوله: git bisect bad 
فيعرف أن المشكلة في نطاق e,f,g 
لو تمام هقوله: git bisect bad

فهيعرف ان المشكلة في نطاق f,g 

وهكرر العملية لحد ما يحدد المشكلة فين وبعدها هقوله: git bisect reset 

عشان يرجع للحالة الي كان عليها قبل حدوث المشكلة

9- git shortlog: 
بيعمل ملخص للـ commits الموجودة في المشروع، وبيجمعها حسب الـ developer اللي عملها.

سيناريو : لو عايز ال commits  ومين عملها من ال team  بتاعي هكتب: 
git shortlog

      Add products
      Fix products

Mahmoud (3):
      Add login
      Fix login
      Update validation


وممكن لو عايز الموضوع بشكل أبسط هكتب: 
git shortlog -s

فهيظهرلي عدد ال commits  لكل شخص 
كمثال:     3  Mahmoud
    2  Ahmed

11- git worktree: 
الأمر ده بستخدمه عشان أعمل أكتر من working directory  لنفس ال repo  
وده مفيد لو عايز أشتغل على أكثرمن branch  بدون ما أعمل checkout  أو stash 

عشان انشأ worktree  بكتب: 

git worktree add <path> <branch>

سيناريو: لو أنا شغال على  feature  وفجأة ظهر bug   في ال main  
فبدل ما كنت هعمل stash  هعمل كالتالي : 
git worktree add ../bug-fix main 

          وبعدها عشان اروح لل  worktree  الجديدة هكتب: 
cd ../bug-fix

لو عايز أحذفها هكتب: git worktree remove ../bug-fix

12- git verify-commit : 
 لو حد عمل Commit ووقّعه بتوقيع رقمي،  بنستخدم git verify-commit علشان نتأكد إن الـ Commit فعلًا موقّع بشكل مضمون وسليم.

سيناريو: في المشروع او لقيت commit  موقع من واحد من ال team  وعايز أتأكد هل فعلا ده توقيعه ولا لا 
هكتب: git verify-commit <commit>

وال commit  هنا هنكتب ال commit hash  

هيظهرلي أحد الردين: 
Good signature → التوقيع صحيح
BAD signature  → التوقيع غير صحيح

13- git filter-repo : 

بستخدمه عشان أقدر على ال repo history  بشكل كامل أو أحذف ملفات 

سيناريو: في أحد ال commits  رفعت بالغلط ملف اسمه password.txt  ودي مشكلة كبيرة لأن حتى لو حذفته من ال commit  الحالي فهو لازال موجود في ال history  وأي حد يقدر يرجعه تاني 
فلازم يتم ازالته بشكل جذري من ال history 
عن طريق: git filter-repo --path passwords.txt --invert-paths

كأني بقوله: عيد كتابة ال history  واحذف ال password.txt  من كل ال commits  

لكن نخلي بالنا من حاجة مهمة: git filter-repo بيعمل rewrite للـgit history، يعني الـ commit hashes القديمة ممكن تتغير.

عشان كده لو الـ repository مشترك مع team ومرفوع بالفعل، لازم نكون حذرين جدًا قبل استخدامه، لأن إعادة كتابة الـ history ممكن تسبب مشاكل لباقي ال team.
